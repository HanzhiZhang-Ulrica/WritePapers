# 各节写作

## 正文与 Appendix 分工

以下指引分为两层：**长期保持的研究与写作规则，以及每篇论文根据仓库、会议和实验重新确定的内容。** 句数、字数和篇幅分配是规划起点，最终以目标会议要求和实际信息量调整。

| 内容           | 正文保留                            | Appendix 展开                  |
| -------------- | ----------------------------------- | ------------------------------ |
| 问题与主要认识 | 完整解释                            | 必要的补充背景                 |
| 核心机制       | 做什么、为什么、关键关系            | 实现参数与特殊路径             |
| 数学           | 决定方法含义的公式                  | 完整推导、边界与性质           |
| 数据表示       | 保存什么、如何被使用                | 位序、offset、buffer shape     |
| 执行           | 数据怎样进入计算、为何适合 workload | 线程、指令、调度条件           |
| 实验           | 主结果、关键趋势、决定性对照        | 完整模型与任务明细             |
| 实验设置       | 对理解比较必需的条件                | 精确版本、命令、种子、计时边界 |
| 讨论           | 主要研究认识                        | 设计取舍、扩展与具体条件       |

> **读者缺少这一段，还能否理解主要解法，并判断核心证据支持什么？**

需要它才能理解，就保留。主要用于重建实现或查找完整结果，就放附录。

## 篇幅建议

对于类似本次的紧凑经验性方法论文，可用下面的比例开始规划，图表占用一并计算：

| 部分         | 全文正文篇幅的初始比例 |
| ------------ | ---------------------- |
| 标题、摘要   | 5%                     |
| Introduction | 15%                    |
| Related Work | 8%                     |
| Method       | 30%                    |
| Experiments  | 39%                    |
| Conclusion   | 3%                     |

理论论文、数据集论文和纯系统论文应按贡献类型重新分配。**目标会议的实际页数规定始终优先。**

## Title

### 目标

读者看到标题就知道：

研究对象 + 主要技术特点 + 应用或目标。

### 详细步骤

1. 识别论文最主要的研究对象。
2. 确定最值得强调的具体设计。
3. 判断标题是否需要方法名。
4. 判断任务或应用是否应该直接出现。
5. 删除泛化但没有具体意义的修饰词。
6. 查询是否已有相同或过于相近的方法名称。
7. 检查标题是否与 Abstract 的主要贡献一致。

例如，`Unified`、`Native`、`Efficient` 可以使用，但需要有具体技术含义；不要连续堆叠。

建议先生成三到五个候选，再选择一个作为全文固定名称。

## Abstract

初稿可控制在约 180–230 个英文词，再根据会议要求和阅读效果调整。

| 句子 | 职责               | 应当让读者知道什么         |
| ---- | ------------------ | -------------------------- |
| S1   | 具体研究场景与价值 | 研究对象和实际目标         |
| S2   | 核心困难           | 哪个结构关系阻碍目标       |
| S3   | 方法身份与主要解法 | 提出了什么                 |
| S4   | 解法的关键能力     | 为什么这个设计值得关注     |
| S5   | 第一项主要机制     | 如何作出关键判断或选择     |
| S6   | 第二项主要机制     | 如何满足另一项核心要求     |
| S7   | 实际实现关系       | 选择怎样成为可用模型或系统 |
| S8   | 最有分量的结果     | 得到了什么可衡量收益       |
| S9   | 研究认识           | 读者应当记住什么设计关系   |

某项机制一句即可说清时，可以合并 S5–S6。确有必要时，增加一句范围说明。代码链接按会议规定处理，不承担研究叙事职责。

**先给足理解背景，再迅速出现解法。** 不用两三句泛谈 AI 或 LLM 的重要性。

**主要结果必须具有可恢复的比较口径。** 最大加速对应哪个参照、什么指标和哪些模型，要在论文中明确；摘要可以简洁表达，实验协议负责完整定义。

Abstract 需要： 主要指标、关键数值、比较对象、质量范围，以及能够支持的方法认识。

Experiments 需要： 具体模型、硬件、batch size、prompt length、output length、baseline backend 和测量协议。

具体位宽、tile size、GPU 型号和 workload 参数，不应在摘要里反复出现。第一次准确说明后，用已经有明确指代的 `precision candidates`、`selected representation` 等承接。

## Introduction

### 第一段

- 引言第一句话直接引出核心目标及其矛盾，以有引用支持的真实应用说明价值，避免泛谈领域重要性

第一段内就要交代相关操作、定性现象及其造成的问题，不堆观察数据。

### 第二段

第二段按方法类别推进，每类在同一句或紧接的一句中说明“做什么、受什么具体约束、因此增加哪项成本或损害哪种能力”，不能只写“粒度不足”“存在取舍”“增加开销”而让读者猜后果，再据此引出本文特有的研究问题。

具体方法名称和逐项比较留给需要它们的位置。

### 核心洞察与难点

困难应解释核心认识落地时必须同时满足的要求，并与后续解法对应。

避免突然出现未经介绍的运行阶段、硬件指令或新统计对象。

However、First、Second 是在确实存在两个耦合困难时可采用的表达形式，不应该成为所有论文的强制句式。

### 方法总述

- 引言的方法总述只保留核心机制及其作用，参数、边界定义、数值技巧、线程和缓存细节进入 Method 或 Appendix

### 结果段

引言结果段只选核心评价维度各一个最有分量的结果，例如质量与效率各一个最佳结果，保留必要参照、指标和适用条件，不罗列全部模型、硬件、baseline、实验范围和消融，也不把局部最佳写成全面优势。

### 贡献

贡献默认组织为三项职责独立、共同支撑主要认识的交付，分别说清建立的能力、解决的关键决策和实现的实际价值；联合设计应强调整体组织及各部分的协同，不擅自把某个档位、参数或实现技巧提升为单独卖点。

贡献标题、Method 小节和实验并不一定一一同名，但应当能相互对应。

避免把“做了更多实验”“支持很多参数”“编写了完整代码”单独列为核心学术贡献。实验承担支撑职责，代码承担实现和复现职责。

## Related Work

Related Work 应比引言更深入地解释选择对象、判据、粒度和执行关系，按技术类别组织，每个类别句主动寻找多篇真正支持共同描述的代表工作，避免一个类别只有一篇论文，也避免为凑数量堆引用；指定 baseline 必须在相关类别中得到引用，其对应的论证应与后文比较形成闭环，但 baseline 清单不是文献范围的上限。

1. 定义这个方向研究什么。
2. 介绍基础或较粗粒度设计。
3. 介绍更局部、更灵活或不同假设的设计。
4. 说明相关判据、表示或执行关系。
5. 提炼这些设计对当前问题的意义。

“由浅入深”指的是理解顺序，不表示较新的方法或较细的粒度必然更好。

> **它在哪个对象上作出什么选择，这个选择决定了什么能力或约束。**

**默认保留类别式写法。** 本文位置已经在 Introduction 讲清时，Related Work 的每段都无需再重复一次方法名称与贡献。

引用某篇工作，是承认学术关系；纳入实验，是执行特定比较。两者的集合可以不同。

## Method

### 概念地图

开头约 3–5 句，说明：

**整体产物、核心对象、主要阶段、阶段之间传递什么。**

总体方法图在这里被引用。图注承担独立阅读，正文承担解释推进，两者无需连续复述相同的完整流程。

### 小节顺序

顺序由方法决定。保持读者能够沿着“输入如何变成结果”前进，同时清楚每一步解决的问题。

| 位置 | 内容                         |
| ---- | ---------------------------- |
| 开头 | 本节决定或实现什么           |
| 定义 | 只引入当前需要的对象与符号   |
| 机制 | 给出操作或公式               |
| 解释 | 用普通语言说明公式表达的关系 |
| 作用 | 说明结果怎样进入下一步       |
| 导航 | 将实现细节指向准确的附录位置 |

### 公式与符号

正文公式应当满足以下一种职责：

**定义核心操作、明确优化目标、描述不可省略的关系、陈述关键结果。**

- 领域常用的 \(X,W,Y\) 等符号优先沿用。
- 同一个对象保持同一符号。
- 只使用一次且自然语言已足够的对象，通常无需另设符号。
- 先说明对象，再出现公式。
- 公式后解释读者需要理解的含义。
- 局部变化、全局目标、全模型分配分别定义。
- 代理目标的性质使用对应范围，不扩展成实际模型损失的保证。

### 硬件与数据移动

必须说清：

**数据在哪里、以什么格式保存、什么时候转换、由谁复用、在哪里计算、结果如何恢复。**

激活准备和权重准备是独立输入时，图中应当在计算节点汇合。持久模型与临时 workspace 应当分别标识。

每个 schedule 的解释采用：

> **Workload 特点 → 相应组织方式 → 直接带来的作用。**

## Experiments

### 设置与顺序

| 部分                          | 主要内容                     |
| ----------------------------- | ---------------------------- |
| 开头                          | 评价目标、主模型与扩展范围   |
| Datasets and Metrics          | 每类任务衡量什么能力         |
| Configuration and Comparisons | 默认配置以及各组对照的职责   |
| Hardware and Measurement      | 平台、主要指标、完整测量范围 |

不是每个技术参数都需要在正文单独解释理由。**需要解释的是实验设计选择**，例如为什么加入长上下文、为什么比较不同粒度、为什么测完整请求。版本、随机种子和 warm-up 等具体参数放协议。

效率主导的论文可以采用：

**效率 → 同一模型的质量 → 更严格的任务条件 → 结构与运行时分析。**

质量主导的论文可以采用：

**质量 → 关键机制 → 扩展条件 → 实际成本。**

决定顺序的是读者最先需要确认的主张。

### 结果与比较

| 句子 | 作用                                 |
| ---- | ------------------------------------ |
| S1   | 承接前一个实验，并说明本实验评价什么 |
| S2   | 简介任务或比较设置                   |
| S3   | 明确主要趋势，告诉读者看哪里         |
| S4   | 给一个或两个代表性数值及比较对象     |
| S5   | 解释结果支持哪项设计                 |
| S6   | 提炼认识或引向下一实验               |

这些职责可以合并，不需要每段都机械写成六句。

应当选择与主张最相关的比较对象，例如最接近的方法、较强的可执行参照、同资源控制或改变了某个关键机制的配置。

**在哪个条件下、哪个指标、相对谁、体现什么价值。**

用事实描述差距，避免评价对方方法“失败”“落后”“无法适应”等缺乏直接证据的结论。

**正文：** 主要趋势、必要数值、核心结论。

**附录：** 完整模型差异、更多条件、具体控制，以及它们与附录设计细节的联系。

放在附录里的表，详细分析就在附录。正文只用简短 pointer 提示扩展结果。

避免每段都以“因此证明我们的方法有效”结束。

### 消融与收益归因

结构消融、评分消融和 runtime 消融回答不同问题。

- 改变放置范围，支持放置自由度的价值。
- 改变评分方式，支持评分机制的价值。
- 保持选定模型、改变执行，支持 runtime 组织的价值。
- 改变校准采样，评价该采样范围内的稳定性。

一个完整方法超过 baseline，并不能自动确定每个组件的独立贡献。不同对照中的倍率也不能直接相减或拆分。

## Appendix

符号表按对象类别组织，包含符号、简短定义及必要维度。它帮助查阅，不能替代正文首次出现时的解释。

每个推导回答一个明确问题。条件、对象和结论范围与正文一致。

简单的排序性质可以说明清楚，但不需要人为包装成大型理论贡献。

对每个表头式 control，至少说明：

**改变了什么、保持了什么、在哪个范围应用、怎样选择。**

随机控制的构造和实际种子存在于代码或记录时，应当准确写入，缺少时不能猜测。

已有且经确认的设置，可以用一句话解决阅读疑问。例如共同 runtime 条件、相同 evaluator 与 metric field、默认校准和采样消融的区别。

用户已经确认匹配的事项，应当记录为已确认事实，并在协议中简明体现。后续检查集中于新增冲突。

图中明确区分：

**模型准备、每次输入准备、计算、重构、输出。**

ASCII 草图可以用于讨论布局，最终 LaTeX 图与 caption 必须与实际数据依赖对应。

## Conclusion

建议一个段落，3–4 句，约 70–110 个英文词。

| 句子 | 职责                                 |
| ---- | ------------------------------------ |
| S1   | 回答全文研究问题                     |
| S2   | 解释主要结果与关键设计关系           |
| S3   | 提炼可迁移认识                       |
| S4   | 必要时指出由该认识直接导出的设计方向 |

Conclusion 无需再次逐项介绍每个组件和所有指标。

> 结果说明了怎样的关系；以后设计同类方法时，应当优先考虑哪一个问题。

## 实验解释与结论的补充要求

如果数据只是观察性关系，解释也应保持观察性。

不需要每句话都重复所有配置；前文已经建立的上下文可以正常继承。

Appendix 中的实验也必须解释趋势和设计意义。

不能因为它放在附录，就只放一张大表而完全不分析。

未来工作只有在自然衔接时才需要提。
