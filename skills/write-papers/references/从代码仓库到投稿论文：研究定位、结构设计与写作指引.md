# 从代码仓库到投稿论文：研究定位、结构设计与写作指引

**最终目标是让读者清楚理解：这项工作解决了什么真实问题，为什么原有设计难以同时满足相关要求，本文抓住了哪个关键关系，以及证据如何支持这个解法。**

这次写作反复确认的一点是：**专业性来自准确的研究判断、清楚的机制解释和完整的证据联系。** 实现细节的数量、术语的复杂程度、公式的密度，都应当服从这个目标。此前的写作计划已经把“工程工作量”和“学术增量”、“观察结果”和“收益归因”、“读者需要的解释”和“重复流程介绍”明确分开。   Pasted markdown(20260913-212834)

以下指引分为两层：**长期保持的研究与写作规则，以及每篇论文根据仓库、会议和实验重新确定的内容。** 句数、字数和篇幅分配是规划起点，最终以目标会议要求和实际信息量调整。

------

## 一、输入、工作方式与最终交付

### 1. 最小输入

以后启动一篇论文，只需要提供：

```
代码仓库：URL、分支或上传的压缩包
目标会议：会议名称、年份、投稿类型
```

仓库中已有的 README、方法文档、实验配置、结果文件、绘图脚本和论文草稿，都应由写作者主动寻找、读取和对应。用户额外提供的旧论文、中文批注和风格样例，作为补充材料。

**代码和会议输入之后，写作者负责完成研究理解与写作规划，不能把任务转化为要求用户安装 skills、配置 local agent 或操作一套自动化系统。** Skills、harness 和博客是需要阅读、判断和吸收的资料。

### 2. 最终交付应当包含什么

| 交付内容        | 必须回答的问题                                       |
| --------------- | ---------------------------------------------------- |
| 会议与领域定位  | 这项工作适合哪个实际投稿类别，目标读者关心什么？     |
| 研究判断        | 工作的学术价值、主要增量和最强证据是什么？           |
| 论文主线        | 全文希望读者记住哪一个中心认识？                     |
| 贡献与证据对应  | 每项贡献由哪段方法、哪个推导、哪组实验支撑？         |
| 正文与附录计划  | 各部分放在哪里，承担什么职责？                       |
| 完整 LaTeX 稿件 | 方法、实验、讨论、结论、图注、引用和附录彼此一致     |
| 最终检查结果    | 引用、符号、范围、数值、格式和阅读障碍是否处理完成？ |

实验已经存在时，直接读取并完成分析。实验仍在运行时，先完成有依据的部分，并为结果保留准确的位置。**“实验尚未完成”和“研究缺少实验设计”必须分开判断。**

## 二、从这次写作中保留下来的核心原则

### 1. 一篇论文围绕一个主要认识展开

方法可以有多个组件，论文应当有一个能够把这些组件联系起来的主要认识。

对 AlignQuant，真正值得记住的是局部精度选择与实际部署结构之间的关系。联合评分、选定表示和阶段专用执行分别服务于这个关系。只把它概括为“使用 Fisher、选择 tile、打包权重、实现 kernel”，会丢失论文层面的研究内容。   Pasted markdown(20260913-212834)

以后每篇论文先写出：

> **本文发现或建立了什么关系，使一个重要目标能够以更有效的方式实现？**

这句话应当能够脱离方法名称、具体超参数和代码文件名独立成立。

### 2. 作者承担解释成本

“让读者容易理解”的具体含义是：作者主动完成指代消解、前提交代、概念连接和结果解释。

读者应当把注意力用于理解和评价研究，而不是用于猜测：

- 这个新名词指什么。
- 这个公式为什么突然出现。
- 这里的变化是局部还是全局。
- 表里的某个 control 究竟改变了什么。
- 哪条曲线支持刚才的结论。
- 一个实现动作为什么能带来所述收益。

此前写作资料对信息顺序和具体指代的建议，最终都落实到这一点：**每个新对象出现时，读者已经有足够的上下文理解它的用途。**    Pasted markdown(20260913-212834)

### 3. 先选择内容，再压缩语言

压缩的优先顺序是：

**移走次要内容 → 删除重复解释 → 合并重复职责 → 精简句子。**

把十个技术概念塞进一个短句，只会提高阅读难度。Farquhar 的建议同样强调，压缩达到一定程度后，应减少句子和次要内容，保留更经过选择的解释。[Sebastian Farquhar](https://sebastianfarquhar.com/on-research/2024/11/04/how_to_write_ml_papers/)

### 4. 每次修改都服务于明确问题

一次修改可以解决分类错误、因果跳跃、技术范围、语法或重复。已经清楚且符合事实的句子应当保持稳定。

用户明确保留的结构、命名和表达，需要记录为既定选择。再次提出修改，应当具有新的事实依据或明确的跨节冲突。

### 5. 强调优势，同时保持事实范围

正文围绕有证据的研究价值组织。方法边界和实验条件用简洁、正向的协议说明表达。

内部审阅可以深入检查问题；最终论文中的主张使用实际得到支持的范围。影响核心结论的条件仍需清楚交代，相关反例和必需披露应当按研究内容及会议要求处理。

## 三、如何学习会议偏好与写作资料

### 1. 会议调研必须逐年进行

收到目标会议后，先核查当年的官方材料：

| 材料                | 提取内容                                      |
| ------------------- | --------------------------------------------- |
| Call for Papers     | 研究范围、贡献类型、实际投稿分类              |
| Author Guidelines   | 页数、附录、匿名、格式、补充材料              |
| Reviewer Guidelines | 审稿标准、证据要求、创新性与重要性的判断方式  |
| 官方模板            | 实际宏定义、标题层级、引用与图表格式          |
| 投稿表单            | Primary area、keywords、track、声明等实际字段 |
| AI、伦理和复现政策  | 需要哪些声明，分别披露什么                    |

**Track、subject area、primary area、workshop 和 presentation type 要分别确认。** 不能因为一篇相关论文获得 oral，就把 oral 当成可选择的投稿 track。会议规范以对应年份的官方页面为依据。[ICLR](https://iclr.cc/Conferences/2027/AuthorGuidelines)

### 2. 近两年相似论文怎样选

建议先形成一个小而有针对性的阅读集合：

| 样本类型               | 建议数量 | 阅读目的                     |
| ---------------------- | -------- | ---------------------------- |
| 技术上最近的论文       | 4–6 篇   | 判断真正的区别与继承关系     |
| 同会议、同类贡献的论文 | 4–6 篇   | 学习问题定位和证据组织       |
| 其中表达特别清楚的论文 | 2–3 篇   | 分析句段职责、图注与阅读节奏 |
| 有公开评审的相关论文   | 2–4 篇   | 识别审稿人实际关注的问题     |

这些数量是阅读预算，不是达到某数量即可完成调研。

每篇记录以下信息：

```
论文名称与版本：
会议、年份及已确认的类别：
核心问题：
一句话主要认识：
真正的新内容：
方法如何组织：
主要证据：
正文与附录如何分工：
摘要各句职责：
引言各段职责：
最值得借鉴的表达：
与当前工作相关的审稿关注：
```

**学习信息组织、解释深度和证据呈现。不要借用对方的研究主张、实验条件或技术事实。**

### 3. 怎样判断适合的投稿领域

归类依据是工作最主要的学术对象。

例如，一个方法包含优化目标，并不自动意味着它应当进入 optimization 类别。需要看贡献主要发生在优化理论、模型行为、数据构建、表示设计、运行系统还是硬件映射。

建议用一句话完成判断：

> 本文主要推进的是 ______ 的研究认识，核心证据来自 ______，因此最适合由熟悉 ______ 的审稿人评价。

### 4. 对 skills 和写作建议进行筛选

本次重新阅读的材料与此前计划共同支持以下取舍：

| 材料                          | 值得采用                                   | 需要自行判断                           |
| ----------------------------- | ------------------------------------------ | -------------------------------------- |
| Nanda 的研究叙事建议          | 少数明确主张、读者价值、证据与主线对应     | 不把某一研究领域的实验标准机械推广     |
| Levin、Redell 的系统论文建议  | 区分新思想和实现工作量；解释选择与所得认识 | 根据当前题型调整组织                   |
| Mensh、Kording 的论文结构建议 | 背景、内容、结论的连接；稳定术语           | 避免让每段都产生完全相同的外形         |
| Farquhar 的 ML 写作建议       | 内容取舍、结果导读、逐层规划               | 摘要句数与 Related Work 位置按本文决定 |
| `deslop`、`humanizer`         | 清除空泛强调、机械对立和重复节奏           | 保留真正有用的专业词、被动语态和标题   |
| ARIS 等 paper-writing skills  | 主张与证据表、分节检查、引用纪律           | 固定页数、固定句数、固定段尾模板不照搬 |
| anti-defensive-writing        | 以成立的价值为中心，明确写出优势           | 用科学证据决定比较范围和结论强度       |

这些资料之间存在差异。例如，有的 skill 要求 Related Work 至少一页，有的反对所有被动句，有的要求每段最后重复本文定位。这些要求与我们最终形成的文风并不一致，不能进入长期硬规则。[Alignment Forum](https://www.alignmentforum.org/posts/eJGptPbbFPZGLpjsp/highly-opinionated-advice-on-how-to-write-ml-papers)    Pasted markdown(20260913-212834)

## 四、阅读代码：先建立研究事实，再形成论文语言

### 1. 分五轮阅读仓库

| 轮次       | 重点读取                                  | 应当得到的认识                         |
| ---------- | ----------------------------------------- | -------------------------------------- |
| 项目结构   | README、目录、入口、配置、方法文档        | 当前工作是什么，主要执行路径在哪里     |
| 核心计算   | 算法、模型、损失、选择规则、主要 kernel   | 输入怎样变成输出，哪些步骤决定方法行为 |
| 数据与执行 | 表示格式、张量形状、缓存、临时数据、调度  | 数值对象在哪里保存、转换、复用和计算   |
| 实验对应   | evaluator、运行脚本、配置、结果和绘图代码 | 每个结果对应哪个模型、方法和测量口径   |
| 主张验证   | 逐项回查可能写成 contribution 的内容      | 实现、数学解释和实验是否支持同一件事   |

README 和 local agent 的总结可以提供入口；关键事实应当追到具体实现和实际配置。

**完整阅读意味着覆盖所有与论文主张有关的路径。** 文件列表、关键字搜索和编译通过，分别只能证明对应范围内的事实。

### 2. 必须建立一张方法事实表

至少包含：

| 项目           | 需要确定的内容                                     |
| -------------- | -------------------------------------------------- |
| 研究对象       | 权重、激活、注意力、缓存、模型结构、数据或其他对象 |
| 输入与输出     | 类型、形状、坐标系、数值含义                       |
| 核心决策       | 选择什么、何时选择、依据什么                       |
| 目标与约束     | 实际优化的量，以及预算或资源限制                   |
| 执行阶段       | 离线、在线、训练、校准、推理                       |
| 持久与临时状态 | 保存什么，生命周期多长                             |
| 关键分支       | 不同 workload、硬件或模型触发哪些路径              |
| 最终评价对象   | 模拟模型、重构模型、原生 kernel 或完整部署模型     |
| 实验对应       | 质量、速度和存储是否来自同一方法配置               |

特别注意区分三个层级：

**设计原则、当前实现、已测范围。**

一个可迁移的设计原则，可以通过某个具体位宽或硬件实现验证；摘要中提高概括层次，并不自动扩大当前代码和实验的支持范围。

### 3. 事实来源按问题类型处理

不要简单地用一个来源覆盖所有其他来源。

- **论文当前范围与已接受命名：** 使用最新稿件和用户最新确认。
- **方法实际执行行为：** 使用相关实现和生效配置。
- **实验数值与测量口径：** 使用最终结果、对应配置和作者确认。
- **旧计划与旧总结：** 用于理解历史，避免混入已经废弃的路径。
- **外部文献事实：** 使用原始论文、官方代码或正式元数据。

发现冲突时，定位具体冲突；不要自动把旧文档当作当前真相，也不要把当前论文中的一句概括当作独立执行验证。

## 五、从代码中识别研究问题、难点与 novelty

### 1. 先做学术判断

写作前回答六个问题：

| 问题                   | 合格答案的特征                             |
| ---------------------- | ------------------------------------------ |
| 为什么值得研究？       | 对某个真实场景、能力或资源问题有影响       |
| 原有设计受到什么约束？ | 能指出具体共享关系、假设、数据流或计算结构 |
| 困难为什么存在？       | 两个或多个要求之间具有实际耦合             |
| 本文改变了什么？       | 一个明确的决策、表示、组织方式或计算机制   |
| 这个改变带来什么能力？ | 能说明新增自由度、可用性、效率或解释能力   |
| 读者学到了什么？       | 能把所得认识用于理解或设计其他方法         |

**Research gap 必须具有实际后果。**

“已有工作没有使用某个组合”只是文献观察。需要继续解释：为什么场景需要这个组合，它解决了什么原有约束，以及这种改变怎样产生有意义的结果。

### 2. 一个可复用的 framing 构造式

先用普通语言填写：

```
在【具体场景】中，系统需要同时实现【目标一】和【目标二】。
现有【决策或表示方式】使【具体对象】受到【具体约束】，影响【实际结果】。
本文通过【核心设计变化】协调这两个要求。
【理论、实现或实验】表明，这个变化带来了【具体能力或收益】。
由此得到的研究认识是【可迁移的设计关系】。
```

这只是内部推敲工具。最终正文应当根据内容写成自然段落。

### 3. 难点写成“需要同时做到什么”

有效的 difficulty 通常来自以下关系：

| 类型         | 要写清的关系                         |
| ------------ | ------------------------------------ |
| 数值与计算   | 更细的数值选择怎样进入规则计算       |
| 局部与全局   | 局部决策怎样服务整体目标             |
| 多阶段共享   | 不同阶段的需求怎样由同一状态满足     |
| 压缩与访问   | 减少存储后怎样维持高效访问           |
| 灵活性与成本 | 增加选择自由度后怎样控制相关开销     |
| 表示与泛化   | 当前表示怎样适应不同输入、任务或规模 |

难点应该从问题中自然出现。普通操作的实现细节无需逐个升格成“核心挑战”。

### 4. Novelty、contribution 和 result 分开

- **Novelty：** 相对于最近邻工作的实质增量。
- **Contribution：** 论文交付给社区的知识、方法、系统或资源。
- **Result：** 支持这些贡献的观察或测量。

“实现了 kernel”“用了梯度”“做了全局排序”各自是否构成贡献，需要结合已有工作和实际作用判断。

这次最稳定的贡献分工是：**组织方式负责提供能力，选择规则负责作出决策，表示与执行负责把选择落实。** 三项贡献既相互连接，又有独立职责。   Pasted markdown(20260913-212834)

### 5. Aim to oral 的实际含义

把目标落实为四项质量：

**问题有分量、认识有辨识度、机制容易解释、证据具有决定性。**

不要用固定模型数、固定 GPU 数、定理数量或夸张措辞替代这些判断。会议展示形式也无法由某种句式保证。

## 六、先建立“主张、机制、证据、位置”的对应表

开始写正文前，完成：

| 主要主张             | 支撑机制               | 直接证据                 | 正文位置                     | 附录位置         |
| -------------------- | ---------------------- | ------------------------ | ---------------------------- | ---------------- |
| 方法实现一种有用能力 | 关键设计变化           | 对应质量或功能实验       | Introduction、Method、主结果 | 额外场景         |
| 某个结构选择有效     | 决策自由度或组织方式   | 固定其他因素的结构对照   | 核心消融                     | 完整控制与定义   |
| 实际运行更高效       | 表示、访问、调度或计算 | 完整路径测量             | 效率主结果                   | 配置、分解与扩展 |
| 某个机制产生收益     | 具体组件               | 直接机制对照             | 必要时正文                   | 详细消融         |
| 方法适用于多个条件   | 共享设计及适配规则     | 对应模型、长度、硬件结果 | 简明范围                     | 完整覆盖         |

这张表可以发现两类问题：某项强主张缺少对应证据，或大量实验无法说明它们对主线的作用。

### 三类陈述必须保持区分

| 陈述                             | 依据                     |
| -------------------------------- | ------------------------ |
| “这个配置达到某个数值”           | 实验结果                 |
| “这个 kernel 怎样读取和转换数据” | 实现                     |
| “这项优化导致某部分收益”         | 能隔离该变化的比较       |
| “这个原则适用于更大范围”         | 对应的理论条件或扩展证据 |

此前效率 framing 的计划已经明确区分了观察、机制与收益归因。这个区分应当成为之后所有文章的固定检查项。   Pasted markdown (2)(10)

## 七、正文与 Appendix 如何分配

### 1. 正文负责让主张成立，附录负责让细节可查

| 内容           | 正文保留                            | Appendix 展开                  |
| -------------- | ----------------------------------- | ------------------------------ |
| 问题与主要认识 | 完整解释                            | 必要的补充背景                 |
| 核心机制       | 做什么、为什么、关键关系            | 实现参数与特殊路径             |
| 数学           | 决定方法含义的公式                  | 完整推导、边界与性质           |
| 数据表示       | 保存什么、如何被使用                | 位序、offset、buffer shape     |
| 执行           | 数据怎样进入计算、为何适合 workload | 线程、指令、调度条件           |
| 实验           | 主结果、关键趋势、决定性对照        | 完整模型与任务明细             |
| 实验设置       | 对理解比较必需的条件                | 精确版本、命令、种子、计时边界 |
| 讨论           | 主要研究认识                        | 设计取舍、扩展与具体条件       |

判断一段内容是否属于正文，可以问：

> **读者缺少这一段，还能否理解主要解法，并判断核心证据支持什么？**

需要它才能理解，就保留。主要用于重建实现或查找完整结果，就放附录。

### 2. 压缩时保留“理解所需的连接”

优先移走位级布局、长配置清单、重复推导和额外模型明细。以下内容应当保留到足以理解的程度：

**对象是什么、操作改变什么、为什么需要这一步、结果怎样进入下一步。**

### 3. 篇幅建议

对于类似本次的紧凑经验性方法论文，可用下面的比例开始规划，图表占用一并计算：

| 部分         | 全文正文篇幅的初始比例 |
| ------------ | ---------------------- |
| 标题、摘要   | 5%                     |
| Introduction | 15%                    |
| Related Work | 8%                     |
| Method       | 30%                    |
| Experiments  | 39%                    |
| Conclusion   | 3%                     |

理论论文、数据集论文和纯系统论文应按贡献类型重新分配。**目标会议的实际页数规定始终优先。**

## 八、Abstract：8–10 句话讲完一个完整研究判断

### 1. 推荐的九句职责

初稿可控制在约 180–230 个英文词，再根据会议要求和阅读效果调整。

| 句子 | 职责               | 应当让读者知道什么         |
| ---- | ------------------ | -------------------------- |
| S1   | 具体研究场景与价值 | 研究对象和实际目标         |
| S2   | 核心困难           | 哪个结构关系阻碍目标       |
| S3   | 方法身份与主要解法 | 提出了什么                 |
| S4   | 解法的关键能力     | 为什么这个设计值得关注     |
| S5   | 第一项主要机制     | 如何作出关键判断或选择     |
| S6   | 第二项主要机制     | 如何满足另一项核心要求     |
| S7   | 实际实现关系       | 选择怎样成为可用模型或系统 |
| S8   | 最有分量的结果     | 得到了什么可衡量收益       |
| S9   | 研究认识           | 读者应当记住什么设计关系   |

某项机制一句即可说清时，可以合并 S5–S6。确有必要时，增加一句范围说明。代码链接按会议规定处理，不承担研究叙事职责。

### 2. 摘要应当保持的平衡

**先给足理解背景，再迅速出现解法。** 不用两三句泛谈 AI 或 LLM 的重要性。

**按读者能理解的因果顺序介绍机制。** 这次后期把 packed representation 放在候选选择之前，读者就难以理解“selected”究竟选择了什么。流程明确之后，可以通过自然主语承接压缩，而不是每句都加 `First`、`Then`。

**参数具体一次即可。** 具体位宽、tile size、GPU 型号和 workload 参数，不应在摘要里反复出现。第一次准确说明后，用已经有明确指代的 `precision candidates`、`selected representation` 等承接。

**主要结果必须具有可恢复的比较口径。** 最大加速对应哪个参照、什么指标和哪些模型，要在论文中明确；摘要可以简洁表达，实验协议负责完整定义。

### 3. 摘要结尾必须增加理解

下面两类结尾的职责不同：

```
结果复述：该方法取得更高速度和良好准确率。
研究认识：某种组织方式使局部选择与规则计算能够同时成立。
```

最后一句应当完成第二项工作。这个认识需要从前面的机制与结果自然得到，避免突然宣布一个范围很大的“普遍原则”。

完整摘要包含背景、内容和结论，也是论文结构研究中反复强调的原则。[PLOS](https://journals.plos.org/ploscompbiol/article?id=10.1371%2Fjournal.pcbi.1005619)

------

## 九、Introduction：五段主线，加职责平行的贡献

建议约 500–700 个英文词。先按句子职责规划，再写成自然段落。

### 第一段：实际目标、共同问题与结构冲突

建议 4–5 句。

| 句子 | 职责                                       |
| ---- | ------------------------------------------ |
| S1   | 说明具体应用面对的资源或能力要求           |
| S2   | 引入相关技术及其共同需要解决的问题         |
| S3   | 说明第一类已有路线怎样处理这个问题         |
| S4   | 说明第二类路线增加了什么自由度             |
| S5   | 指出这项自由度进入实际场景时遇到的结构冲突 |

这次 Introduction 的一个重要修正是：**先建立低精度带来的准确率问题，再介绍统一精度和混合精度两条路线。** 两种技术因而有共同的问题背景。

### 第二段：已有设计如何处理冲突，最后提出研究问题

建议 5–6 句。

| 句子 | 职责                                   |
| ---- | -------------------------------------- |
| S1   | 引用动机图，指出读者应当关注的关系     |
| S2   | 概括第一类已有设计及其共享范围         |
| S3   | 概括第二类设计及其增加的选择           |
| S4   | 说明相关系统或表示设计如何实现这些选择 |
| S5   | 提炼仍需协调的具体要求                 |
| S6   | 提出全文唯一的核心研究问题             |

默认在这里按方法类别写，引用提供文献归属。具体方法名称和逐项比较留给需要它们的位置。

**问题应由前文推导出来。** `remains unexplored`、`has received little attention` 不能单独承担研究动机。

### 第三段：主要认识、支持观察与真正的难点

建议 5–7 句。

| 句子 | 职责                             |
| ---- | -------------------------------- |
| S1   | 直接提出关键设计认识             |
| S2   | 解释它新增的能力                 |
| S3   | 给出支持该认识的观察或代表性证据 |
| S4   | 说明把认识落实为方法还需满足什么 |
| S5   | 第一个困难                       |
| S6   | 第二个困难                       |
| S7   | 必要时明确两项困难为什么相关     |

避免突然出现未经介绍的运行阶段、硬件指令或新统计对象。

### 第四段：总体解法与两个回答逐一对应

建议 4–5 句。

| 句子 | 职责                             |
| ---- | -------------------------------- |
| S1   | 方法名称、方法类型及整体目标     |
| S2   | 回答第一个困难                   |
| S3   | 回答第二个困难                   |
| S4   | 说明两个回答如何形成完整方法     |
| S5   | 必要时补充一个不可缺少的执行关系 |

**这里只保留流程节点和节点作用。** 具体梯度平方、scale-search 网格、prefix offset 和线程配置进入 Method 或 Appendix。

### 第五段：主结果与研究意义

建议 2–3 句。

第一句给最主要的结果及必要范围。第二句说明质量、资源或扩展范围中的互补证据。最后一句提炼这些结果支持的研究认识。

### Contributions：默认三项，每项一到两句

贡献按职责区分，例如：

```
C1：建立一种组织方式，使什么能力成立。
C2：提出一种关键决策规则，解决什么选择问题。
C3：将其实现为可用系统或模型，完成什么实际功能。
```

贡献标题、Method 小节和实验并不一定一一同名，但应当能相互对应。

避免把“做了更多实验”“支持很多参数”“编写了完整代码”单独列为核心学术贡献。实验承担支撑职责，代码承担实现和复现职责。

## 十、Related Work：按设计选择组织，读完能定位本文

### 1. 默认三个主题段

主题应当来自当前工作的最近邻关系。对 AlignQuant，三个方向是精度分配、表示与执行、变换辅助量化；其他论文应重新确定。

每段建议 4–6 句：

1. 定义这个方向研究什么。
2. 介绍基础或较粗粒度设计。
3. 介绍更局部、更灵活或不同假设的设计。
4. 说明相关判据、表示或执行关系。
5. 提炼这些设计对当前问题的意义。

“由浅入深”指的是理解顺序，不表示较新的方法或较细的粒度必然更好。

### 2. 每种方法需要说明什么

一句话至少交代：

> **它在哪个对象上作出什么选择，这个选择决定了什么能力或约束。**

例如，精度共享的说明应当让读者知道哪些权重共同接受同一个决策。这样的结构事实，比统一追加“产生额外开销”更有信息量。

### 3. 优点与约束怎样自然出现

避免每句话都变成相同模式：

```
方法 A 有一个优点，但是存在一个缺点。
方法 B 有一个优点，但是存在一个缺点。
方法 C 有一个优点，但是存在一个缺点。
```

把真实差异放入动作和作用范围：

```
Channel-level allocation shares one precision across an output feature, coupling the precision choices of its input weights.
```

句子解释了方法本身，也让读者理解共享范围。

**默认保留类别式写法。** 本文位置已经在 Introduction 讲清时，Related Work 的每段都无需再重复一次方法名称与贡献。

### 4. 引用与实验比较分别处理

引用某篇工作，是承认学术关系；纳入实验，是执行特定比较。两者的集合可以不同。

但描述相关工作之前，应当实际阅读其方法和结果。已有技术的归属越准确，本文的实质区别越容易成立。[USENIX](https://www.usenix.org/legacy/publications/library/proceedings/dsl97/good_paper.html)

## 十一、Method：按理解顺序展开，关键步骤都有理由

### 1. 先给读者一张概念地图

开头约 3–5 句，说明：

**整体产物、核心对象、主要阶段、阶段之间传递什么。**

总体方法图在这里被引用。图注承担独立阅读，正文承担解释推进，两者无需连续复述相同的完整流程。

### 2. 小节按因果关系组织

通常采用 3–4 个核心小节，例如：

```
构造或表示
关键决策
实际执行
必要的分析或性质
```

顺序由方法决定。保持读者能够沿着“输入如何变成结果”前进，同时清楚每一步解决的问题。

### 3. 每个核心小节的内部顺序

| 位置 | 内容                         |
| ---- | ---------------------------- |
| 开头 | 本节决定或实现什么           |
| 定义 | 只引入当前需要的对象与符号   |
| 机制 | 给出操作或公式               |
| 解释 | 用普通语言说明公式表达的关系 |
| 作用 | 说明结果怎样进入下一步       |
| 导航 | 将实现细节指向准确的附录位置 |

例如，一个评分公式之后，应当直接解释：

> 分数同时考虑变化有多大，以及受影响的输出对目标有多重要。

这类解释替读者完成从符号到方法含义的转换。

### 4. 公式只为必要关系服务

正文公式应当满足以下一种职责：

**定义核心操作、明确优化目标、描述不可省略的关系、陈述关键结果。**

符号规则：

- 领域常用的 \(X,W,Y\) 等符号优先沿用。
- 同一个对象保持同一符号。
- 只使用一次且自然语言已足够的对象，通常无需另设符号。
- 先说明对象，再出现公式。
- 公式后解释读者需要理解的含义。
- 局部变化、全局目标、全模型分配分别定义。
- 代理目标的性质使用对应范围，不扩展成实际模型损失的保证。

### 5. 解释硬件与数据移动

必须说清：

**数据在哪里、以什么格式保存、什么时候转换、由谁复用、在哪里计算、结果如何恢复。**

激活准备和权重准备是独立输入时，图中应当在计算节点汇合。持久模型与临时 workspace 应当分别标识。

每个 schedule 的解释采用：

> **Workload 特点 → 相应组织方式 → 直接带来的作用。**

例如，多行激活带来权重复用，单行输入需要从输出维与归约维提供并行任务。具体提速幅度留给实验。

### 6. 粗体的规则

**标题负责定位，段内粗体负责强调关键关系。**

已有 `\paragraph{...}` 时，后面不要再添加一个同级的段首粗体标题。普通段落也不必全部改造成带粗体名称的小卡片。

每个较长段落通常只强调一个值得记住的机制或结论，例如：

```
The budget \textbf{determines how many tiles receive lower precision}, while the scores determine their locations.
```

不要把每次出现的 tile、scale、INT8 和模型名称都加粗。

## 十二、Experiments：每个实验推进一个判断

### 1. Setup 说明“为什么测”和“怎样比较”

正文 Setup 可采用一个开头段和三个短主题段：

| 部分                          | 主要内容                     |
| ----------------------------- | ---------------------------- |
| 开头                          | 评价目标、主模型与扩展范围   |
| Datasets and Metrics          | 每类任务衡量什么能力         |
| Configuration and Comparisons | 默认配置以及各组对照的职责   |
| Hardware and Measurement      | 平台、主要指标、完整测量范围 |

不是每个技术参数都需要在正文单独解释理由。**需要解释的是实验设计选择**，例如为什么加入长上下文、为什么比较不同粒度、为什么测完整请求。版本、随机种子和 warm-up 等具体参数放协议。

### 2. 实验顺序服务于论文主线

效率主导的论文可以采用：

**效率 → 同一模型的质量 → 更严格的任务条件 → 结构与运行时分析。**

质量主导的论文可以采用：

**质量 → 关键机制 → 扩展条件 → 实际成本。**

决定顺序的是读者最先需要确认的主张。

本次形成的质量链条尤其值得保留：

**General 评价基本能力；长上下文增加证据定位与组合要求；LV-Eval 提供多类问答任务；LongEval 用更密集的长度变化观察检索行为。**

### 3. 一个主结果段的推荐职责

建议 4–6 句：

| 句子 | 作用                                 |
| ---- | ------------------------------------ |
| S1   | 承接前一个实验，并说明本实验评价什么 |
| S2   | 简介任务或比较设置                   |
| S3   | 明确主要趋势，告诉读者看哪里         |
| S4   | 给一个或两个代表性数值及比较对象     |
| S5   | 解释结果支持哪项设计                 |
| S6   | 提炼认识或引向下一实验               |

这些职责可以合并，不需要每段都机械写成六句。

### 4. 结果分析必须包含比较

避免拉踩 baseline，不等于回避 baseline。

应当选择与主张最相关的比较对象，例如最接近的方法、较强的可执行参照、同资源控制或改变了某个关键机制的配置。

比较句应当说明：

**在哪个条件下、哪个指标、相对谁、体现什么价值。**

用事实描述差距，避免评价对方方法“失败”“落后”“无法适应”等缺乏直接证据的结论。

### 5. 消融单独承担归因

结构消融、评分消融和 runtime 消融回答不同问题。

- 改变放置范围，支持放置自由度的价值。
- 改变评分方式，支持评分机制的价值。
- 保持选定模型、改变执行，支持 runtime 组织的价值。
- 改变校准采样，评价该采样范围内的稳定性。

一个完整方法超过 baseline，并不能自动确定每个组件的独立贡献。不同对照中的倍率也不能直接相减或拆分。

系统写作资料同样区分总体比较与设计分解，二者共同建立方法为何有效的解释。[Irene Zhang](https://irenezhang.net/blog/2021/06/05/hints.html)

### 6. 正文与附录的结果分析各自完整

**正文：** 主要趋势、必要数值、核心结论。

**附录：** 完整模型差异、更多条件、具体控制，以及它们与附录设计细节的联系。

放在附录里的表，详细分析就在附录。正文只用简短 pointer 提示扩展结果。

### 7. 每个实验结束后，读者应当增加一种认识

例如：

```
优势在哪类请求更明显。
哪一维精度自由度对质量有用。
某种表示怎样让存储可调而执行保持相近。
某项复用怎样同时作用于两个阶段。
不同模型怎样通过同一规则得到不同的有效选择。
```

避免每段都以“因此证明我们的方法有效”结束。

## 十三、Appendix：按查阅任务组织，控制重复

### 推荐结构

| 部分                                     | 职责                           |
| ---------------------------------------- | ------------------------------ |
| A. Notation and Reading Guide            | 符号表与阅读入口               |
| B. Numerical or Algorithmic Construction | 候选、变换、算子、数值细节     |
| C. Data and Calibration Procedure        | 数据构造、观测、梯度或训练过程 |
| D. Derivations and Properties            | 完整推导、性质与条件           |
| E. Representation and Execution          | 存储、寻址、数据移动、调度     |
| F. Design Rationale                      | 关键选择的理由及适用关系       |
| G. Experimental Protocols                | 精确实验与测量定义             |
| H. Additional Results and Analysis       | 完整结果与深入分析             |

这是本次方法适合的结构，其他论文可以合并或替换相应部分。

### 1. 符号表

符号表按对象类别组织，包含符号、简短定义及必要维度。它帮助查阅，不能替代正文首次出现时的解释。

### 2. 推导

每个推导回答一个明确问题。条件、对象和结论范围与正文一致。

简单的排序性质可以说明清楚，但不需要人为包装成大型理论贡献。

### 3. 消融定义

对每个表头式 control，至少说明：

**改变了什么、保持了什么、在哪个范围应用、怎样选择。**

`Output-row`、`Red.-col`、`Proj./layer` 和 `Random` 这样的名称本身不足以完成定义。随机控制的构造和实际种子存在于代码或记录时，应当准确写入，缺少时不能猜测。

### 4. 协议澄清

已有且经确认的设置，可以用一句话解决阅读疑问。例如共同 runtime 条件、相同 evaluator 与 metric field、默认校准和采样消融的区别。

用户已经确认匹配的事项，应当记录为已确认事实，并在协议中简明体现。后续检查集中于新增冲突。

### 5. 数据移动图

有必要时最多用一两张聚焦图，分别说明不同关系，例如权重准备与共享激活处理。

图中明确区分：

**模型准备、每次输入准备、计算、重构、输出。**

ASCII 草图可以用于讨论布局，最终 LaTeX 图与 caption 必须与实际数据依赖对应。

## 十四、Conclusion：让读者带走一个有用的认识

建议一个段落，3–4 句，约 70–110 个英文词。

| 句子 | 职责                                 |
| ---- | ------------------------------------ |
| S1   | 回答全文研究问题                     |
| S2   | 解释主要结果与关键设计关系           |
| S3   | 提炼可迁移认识                       |
| S4   | 必要时指出由该认识直接导出的设计方向 |

Conclusion 无需再次逐项介绍每个组件和所有指标。

更合适的收束方式是：

> 结果说明了怎样的关系；以后设计同类方法时，应当优先考虑哪一个问题。

这里的启发应当具体到设计行动，例如优先选择可存储、可计算的决策单元，再分配精度。避免泛泛地说“为未来研究开辟新方向”。

## 十五、说人话、减少 AI 味：执行到句子与段落

### 1. 固定的语言限制

| 限制                       | 执行方式                                                     |
| -------------------------- | ------------------------------------------------------------ |
| 禁止否定式包装             | 清除 `not ... but ...`、`rather than`、`not only ...` 等用否定建立重要性的句式 |
| 禁止句中破折号             | 将插入解释改成独立句、从句或必要括号                         |
| 不主动使用 `static`        | 直接描述共享、复用、离线确定等实际关系                       |
| 避免自造封装词             | 优先使用领域已有、含义清楚的名称                             |
| 避免 `frontier` 等空泛总结 | 直接说明质量、存储、速度及它们的关系                         |
| 避免 W4/W8/A8 式正文缩写   | 采用完整位宽表达；公式和代码标识保持准确                     |
| 缩写首次展开               | 包括 TTFT、TPOT、NLL 等读者需要理解的指标                    |
| 保持术语一致               | 同一对象不为追求词汇变化而频繁换名                           |

**技术语义保留。** `negative log-likelihood`、数学减号、不等式以及 `mixed-precision` 中的连字符，都不属于应当机械删除的否定式包装或插入破折号。

真实转折也应保留。`However` 可以引入准确率需求与部署条件之间的实际冲突，问题在于是否具有真实的逻辑作用。

### 2. 主语自然接力，避免连续 `We do ...`

可以让句子依次以实际对象作为主语：

```
Calibration estimates the effect of each precision choice.
The resulting scores determine the selected representation.
Packed weights supply the operands used during inference.
```

这比每句都写 `We first`、`We then` 更自然。适当被动语态也可以使用，不必执行“全文所有句子主动语态”的僵硬规则。

### 3. 转折和连接词必须对应真实关系

- `Therefore`：后句确实由前句推出。
- `However`：存在需要读者注意的真实转折。
- `For example`：后句是前述概念的具体实例。
- `This score`、`This representation`：明确指代。
- `These results`：指向清楚的一组证据。

“流程先后”可以依靠对象传递表达，不需要每个动作都配一个引导词。

### 4. 每段都应有新增信息

常见需要删除的模式：

```
段首预告将介绍某机制。
中间介绍机制。
段尾再次概括已经介绍该机制。
下一段重新预告整个流程。
```

段尾应当增加作用、结论或下一步需要的信息。`deslop` 与 `humanizer` 对机械节奏、模板式收尾和空泛强调的提醒有参考价值，但技术写作仍应保留自己的正式语域与准确对象。[GitHub](https://github.com/stephenturner/skill-deslop/blob/main/SKILL.md)

### 5. 把空泛意义改成具体关系

| 空泛表达         | 更有信息的写法                     |
| ---------------- | ---------------------------------- |
| 提高了整体效率   | 指出减少哪项工作或提高哪个完整指标 |
| 提供灵活性       | 指出哪个对象能够独立选择什么       |
| 增强鲁棒性       | 指出在什么变化范围内保持什么表现   |
| 实现无缝衔接     | 说明前一步产生什么，后一步怎样使用 |
| 显示广泛意义     | 提炼一个能够迁移的设计判断         |
| 结果令人印象深刻 | 给出参照、数值、条件与用途         |

### 6. 借鉴小说和剧本的适用部分

值得采用的是**场景、目标、冲突、推进与回收**。

| 叙事技巧       | 论文中的应用                     |
| -------------- | -------------------------------- |
| 场景具体       | 明确 workload、对象与运行环境    |
| 目标明确       | 说明需要同时实现什么             |
| 冲突真实       | 来自实际约束之间的耦合           |
| 每个场景有作用 | 每段必须推进一个必要理解         |
| 信息逐渐具体   | 概念、机制、公式、证据依次展开   |
| 前后呼应       | 引言的问题在实验和结论中得到回答 |

John August 的场景写作建议中，判断某个场景承担什么必要功能、删除后会丢失什么、应该分配多少篇幅，适合转化为段落编辑方法。论文中的主要发现应当尽早出现，后文负责解释和建立证据。[John August](https://johnaugust.com/2007/write-scene)

### 7. 哲学式思考的作用

对一个现象依次询问：

**观察到了什么；什么机制能够解释；改变哪个因素会改变结果；这个解释适用于哪些条件。**

它能帮助区分相关现象与因果解释，尤其适合设计消融和判断结果归因。科学解释中对反事实与干预关系的讨论，为这种检查提供了有用框架。[Stanford Encyclopedia of Philosophy](https://plato.stanford.edu/entries/causal-explanation-science/)

## 十六、数据、图表和引用的长期检查规则

### 1. 数值方向必须准确

PPL、误差、延迟和能耗通常是越低越好；准确率和吞吐通常是越高越好。具体方向以指标定义为准。

本次最后关于 PPL 的讨论也应保留为一个教训：**PPL 可以增加；需要调整的是叙述重点，数值方向保持准确。**

例如，真实差值为 0.08–0.16 时，可以根据句子需要写：

```
with absolute perplexity differences of 0.08 to 0.16 relative to BF16
```

或：

```
while keeping perplexity within 0.16 of BF16
```

`within` 更适合表达一个上界；差值范围使用 `differences of ...`。不能为强调质量保持而把实际上升写成 PPL improvement。

### 2. 比较条件与指标不可混用

重点检查：

**TPOT speedup 与 throughput ratio；微算子与完整请求；名义位宽与 packed bytes；权重存储与常驻内存；基准长度等级与实际 token 数；单模型多硬件与多模型单硬件。**

一个最高数值要能追溯到明确的比较对象。

### 3. 图表各自回答一个问题

图注至少让读者理解对象、坐标、比较范围、指标方向和必要条件。复杂 panel 需要说明行、列和 panel 内横轴分别代表什么。

所有正文图表都应被实际引用。详细分析与对应图表放在同一部分。

### 4. 引用检查分两层

**技术检查：** citation key 存在、label 唯一、引用目标有效。

**语义检查：** 引用内容确实支持当前句子，附录指向确实包含所承诺的细节，图表比较与文字相符。

BibTeX 的作者、标题、年份、venue、页码和正式版本要核实。不要凭论文年份构造 volume，也不要自动认定不熟悉的新论文 metadata 有误。

### 5. LaTeX 修改应考虑真实宏定义

`\eqref` 的行为取决于当前加载的宏文件和包。先读取实际定义，再修复引用。一个 subsection 保留一个语义明确的 label；修改 label 时同步全部引用。

删除表格列时，同时检查 column specification、表头、单位行、数据行和 caption。

## 十七、修改流程与交付格式

### 1. 从完整草稿到定稿的顺序

推荐流程是：

**研究事实 → framing 与贡献 → 主张证据表 → 句段计划 → Method 与实验 → Appendix → Introduction 与 Related Work → 最终 Abstract 与 Conclusion → 全文检查。**

早期可以先写一个工作版摘要帮助聚焦。最终摘要则吸收已经稳定的方法、结果和主张。

### 2. 逐句修改的固定格式

用户要求修改现有文字时，每项包含：

**位置：** section、paragraph、准确原句，必要时给当前文件行号。

**原文**

```
这里放当前文件中的完整原句。
```

**修改后**

```
这里放可以直接替换的完整句子。
```

**原因**

说明具体解决的阅读、逻辑、技术或格式问题。避免只写“更专业”“更清晰”。

原句必须来自当前文件，不能重新翻译一遍再当作原文。没有批注且无必要联动的部分保持不动。

### 3. 后期排版锁定后的规则

正文已经排好时，优先采用等长或更短的替换。新的配置说明和推导进入附录。确实需要增加正文信息时，指出其必要性，并从同一区域移走等量冗余。

**字符数或词数减少不能保证页数不变。** 图表浮动、数学换行和段尾变化仍需通过完整编译检查。

### 4. 对修改意见建立状态

每个争议项记录为：

```
已接受
已修改
作者确认
保留原文
等待数据
需要进一步核对
```

后续检查使用这些状态。已经拒绝的措辞建议不应不断重新列为“必须修改”；已经确认的实验条件也不应仅凭旧疑点反复要求重查。

## 十八、以后可直接使用的总指令

下面这段可以与本指引一起用于新的论文项目。

```
请根据我提供的代码仓库和目标会议，完成研究理解、会议定位、写作规划和完整论文撰写。

输入：
代码仓库：【URL、分支或上传文件】
目标会议：【名称、年份、投稿类型】

先阅读仓库中的当前实现、配置、实验与结果，识别实际生效的方法路径。README 和 agent 总结用于导航，关键主张必须对应具体实现或证据。区分设计原则、当前实现和已测范围。已有配置主动从仓库寻找，缺失信息集中处理，禁止编造结果、参数、引用和实现能力。

逐年核查会议官方要求、审稿标准、实际投稿类别、模板及声明政策。阅读近两年最相似的论文、相关公开评审和清晰的写作样例，学习其信息组织与证据要求。Skills 和博客作为阅读材料，由你直接吸收判断，不要求我安装或调用任何写作工作流。

先客观判断学术价值，再确定 framing。明确实际场景、重要目标、结构性困难、核心认识、具体机制、最近邻区别和贡献。Research gap 必须解释真实需要与实际收益。论文围绕一个主要认识展开，默认两到三项职责平行的贡献。

建立“主张、机制、证据、正文位置、附录位置”的对应关系。主要机制与决定性证据放正文，完整推导、实现参数、协议及扩展结果放附录。核心论证在当前提交中完整，额外研究可以留待后续。

默认结构为 Abstract、Introduction、Related Work、Method、Experiments、Conclusion 和 Appendix，按题型调整。摘要约8至10句，引言五段加贡献列表，Related Work按研究类别组织，Method按理解与因果顺序展开。句数是规划工具，最终文字保持自然。

先说明对象、目的和必要条件，再介绍操作或公式。每个关键设计说明它解决什么、产生什么、如何进入下一步。沿用领域常用符号，控制新术语数量，缩写首次展开。避免在摘要重复具体位宽、尺寸和配置。

每个实验先简要说明评价目的和任务，再写趋势、代表性比较、设计解释和结论。明确优势出现的条件，适当比较相关强基线，使用事实表达。结构、评分和runtime消融分别承担对应归因。正文与附录各自分析自己的图表。所有数值、范围、方向和比较条件保持一致。

正文采用正向、直接、有具体对象的表达。禁止not…but、rather than、not only等否定式包装，禁止句中插入破折号，不主动使用static，不使用空泛封装与反复免责声明。正常专业术语、连字符和数学符号保留。减少连续We开头、机械First/Then、重复段尾总结及同形句式。段内粗体只强调少量核心关系，已有paragraph标题后不再添加同级粗体标题。

Conclusion回答研究问题并提炼可迁移的设计认识，避免重复摘要的组件清单。

已有稿件的修改先分析，逐项给出准确位置、原文code fence、修改后code fence和具体原因。保持已确认的结构与措辞，只改必要部分。正文排版锁定后默认不增加字数，新增细节优先进入附录。

最后检查引用存在性与语义、公式与符号、图表与文字、模型硬件覆盖、单位与指标、对照定义、正文附录衔接、typos和实际编译效果。明确说明检查范围，不把源码检查等同于执行验证。

研究结果不足以填满某个位置时，完成其余有依据的正文并标明待填内容。不要用假数据或额外包装填补证据。
```

## 最终验收：读者应当能回答的六个问题

**问题是什么，为什么值得解决？**

**困难来自哪个具体关系？**

**本文改变了什么，这个改变为什么有效？**

**与最接近的已有设计相比，实质增量在哪里？**

**哪些证据支持效果、机制和适用范围？**

**读完之后，我在设计或理解同类方法时，可以采用什么新的判断？**

这六个问题都有清楚答案时，文章就具有了这次写作最值得保留的品质：**研究价值集中，解释顺畅，技术准确，证据完整，读者能够记住一个有用的认识。**
